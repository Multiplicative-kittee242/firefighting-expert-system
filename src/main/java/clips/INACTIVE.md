# Inactive & abandoned features fed by the `clips` read path

Some of `ClipsEngineAccess`'s read-path queries and a few GUI groups exist and are fully wired, yet produce nothing visible when the app runs. This file is the forensic record of **why**, kept out of [`README.md`](README.md) so that file can describe the layer rather than its loose ends. The three cases are genuinely different, and the difference matters to anyone deciding whether to finish or delete them:

| Feature | State | Nature |
|---|---|---|
| `FIRE_HOSE` button click | Buttons render, click does nothing | **Inactive** — populated, only the write-back is missing |
| Portable extinguishers (write-back) | Read path live, write path unreachable | **Inactive by design** — staged rollout |
| Border-routed hydrant assignment (`HydrExt*`) | Graph built, assignment never runs | **Abandoned** — an unfinished rule-base half |

Where noted, claims below were confirmed by **live CLIPSJNI tracing** (`watch focus` / `watch rules` plus direct fact-slot dumps), not by reading `feis.clp` text alone.

## 1. `FIRE_HOSE` button — a working, populated group with an unwired click

Unlike the `HydrExt*` scaffolding above, `FIRE_HOSE` (`gui.map.view.FireHoseButtonGroup`) is the one hydrant group that actually renders buttons in practice — one per hydrant outlet CLIPS's routing algorithm allocated to a fire-line location's defense, read from `fireLineHydrantOutletsByLocation` (backed by `hydrants-here`, confirmed across all seven golden scenarios to always equal that field's list size for a given location — never `hydrants-need`, the still-outstanding count; see `ClipsEngineAccess.getFireLineHydrantsPresent`'s javadoc for why `here`/`need` move in lockstep, `here + need` staying equal to the fixed original requirement).

Clicking one of these buttons today only toggles its own Swing selected state (red/green repaint) — `DeckMapController` never attaches an `ActionListener`/`InputAction` to any `HydrantButtonGroup`, unlike every `gui.map.input` group. Nothing is sent back to CLIPS and no other Java state changes. Presumed to be an **inactive confirmation feature**, not an oversight: the domain meaning that fits is the operator marking that a specific allocated hydrant's hose has actually been run out and put into action by the crew, since `hydrants-here` only reflects the routing algorithm's own (virtual) allocation, not physical completion. Unlike the `HydrExt*` scaffolding above, this is inference from naming/semantics, not confirmed by tracing an abandoned rule — noted here so a future implementer knows this button is already populated correctly and only needs the write-back path added, not finished rule-base work.

## 2. Portable extinguishers — read path live, write path inactive by design

`EXTINGUISHER` recommends devices via `get-extinguishers-for-location` (unused, i.e. `used no`, at a fire location) — `ExpertSystemService.getExtinguishersForLocation` renders these into the actions table exactly like every other recommendation. `feis.clp`'s own `IMMEDIATE-EXTINGUISHERS::use-local` printout rule is untouched and keeps firing independently; the two paths simply describe the same guard from two different outputs (console vs. table).

The *report-back* half (`reportExtinguisherUsed` / `ClipsReportService.reportExtinguisherChanges` / `clips.values.internal.ExtinguisherClipsStatus`) exists and is fully wired end-to-end, but is currently unreachable from the GUI: `gui.map.input.ExtinguisherButtonGroup` has no `topology.yaml` button-placement data yet, so it is always constructed with zero elements and never creates a button, and its `GroupKey.EXTINGUISHERS_GROUP` is deliberately absent from every `MapLayerVisibilityManager` phase rule (defaulting to hidden). This is intentional (not a bug) — the feature is being introduced in a read-only, no-user-feedback stage first; `ExtinguisherButtonGroup`'s own javadoc explains why it stays inactive.

## 3. Border-routed hydrant assignment — scaffolded, never finished

Three GUI groups are fully wired but never render a single button in practice: `gui.map.view.HydrExtButtonGroup` (`GroupKey.HYDR_EXT`), `HydrExtBButtonGroup` (`HYDR_EXT_B`), and `HydrExtBFromButtonGroup` (`HYDR_EXT_B_FROM`). Unlike the extinguisher case above, this is **not** a deliberately staged rollout — it is an abandoned rule-base half, confirmed by live CLIPSJNI tracing, not by reading `.clp` text alone.

**What the three groups read.** Each backs onto a different `ClipsEngineAccess` query: `getExtForLocation` (`get-ext-for-location`, direct `ext-edge` assignment → `HYDR_EXT`), `getExtBToForLocation` (`get-ext-b-to-for-location`, the `to` side of an `ext-graph` border route → `HYDR_EXT_B`), and `getExtBFromForLocation` / `getGraphFromLocations` (`get-ext-b-from-for-location` / `get-graph-from-locations`, the `from` side of the same route → `HYDR_EXT_B_FROM`). All three ultimately read the `hydrants-titles` multislot of `ext-edge` facts or the `hydrants-b-titles` multislot of `ext-graph` facts.

**The graph-building and planning halves work.** A live trace of fire scenarios A and D shows `EXTINGUISHING-GRAPH`/`EXTINGUISHING-PLAN` genuinely get focus and run to completion — `make-graph-marginal`, `by-border`, `start-arrays`, `fill-arrays`, `decompose-arrays` all fire, `ext-edge`/`ext-graph` facts are created, and `to-needs`/`by-border` are computed correctly on them (matching the golden-master snapshots). `EXTINGUISHING-PLAN::create-plans` goes further and asserts a `plan` fact (`number`/`location`/`from`) per chosen border route — the routing decision itself is made correctly. None of this is broken.

**The assignment half was never written.** A direct dump of the resulting facts shows `hydrants-titles`/`hydrants-b-titles` sitting at their template default — empty — and `status` on `ext-edge` stuck at its default `wait`, because there is no rule that ever advances it (the `fire-line-location` path this mirrors has exactly such a rule, `HYDRANTS-SEARCH::initiate`, triggered once `hydrants-need != 0`; nothing analogous exists for `ext-edge`/`ext-graph`). Confirmed statically too: across all of `feis.clp`, `hydrants-titles`/`hydrants-b-titles` are only ever `modify`-ed on `fire-line-location` facts (the working `FIRE_HOSE` path) — never on `ext-edge` or `ext-graph`. Nothing ever reads the computed `plan` facts back into those slots either — `EXTINGUISHING-CLEAR::clear-plan` just retracts each `plan` fact once used, so the routing decision is made and then thrown away. The summarizing `deffunction MAIN::get-ext-hydr` (meant to total up hydrants across both multislots) is defined but has no caller anywhere in the rule base — the other half of the same unfinished piece.

**Net effect.** `HydrantButtonGroup.createVisibleButtons` only ever enables a button for a title actually present in the data; since these three groups' backing maps are always empty, they sit at zero buttons and — because `MapLayerVisibilityManager`'s `FIREFIGHTING` rule shows them `showIfEnabled` rather than unconditionally — stay invisible indistinguishably from being absent, even though `assembly.yaml` gives all three real placement config and nothing in the Java wiring is broken. `FIRE_HOSE` (fire-line hydrants, LOCALIZATION phase) is an entirely separate, working code path and is unaffected.

**The click-handler gap applies here too.** Like `FIRE_HOSE` (§1 above), none of the three `HydrExt*` groups is wired to an `ActionListener`/`InputAction` in `DeckMapController` — confirmed by grepping it for every `HydrantButtonGroup` subtype, none appears next to `addActionListener`/`attachInputAction`. Even once the assignment rule above is written and these buttons start rendering, clicking one would still do nothing until that same write-back wiring is added.

**Options for whoever picks this up:** write the missing `ext-edge`/`ext-graph` assignment rule (mirroring `HYDRANTS-SEARCH`/`HYDRANTS-ALLOCATION`) and add the click write-back, or remove the dead path (three query methods, three button groups/controls, `get-ext-hydr`) since `FIRE_HOSE` already gives the operator equivalent hydrant-deployment information.
