# CLIPS integration tests specifics

Inherits project-wide conventions (code style, architecture) from the project's root [`AGENTS.md`](../../../AGENTS.md) and test conventions (DAMP, Hamcrest, naming, fixtures) from [`test/java/AGENTS.md`](../../test/java/AGENTS.md).

**CODESTYLE is mandatory** for every new or edited Java file here: before editing, read [`CODESTYLE.md`](../../../CODESTYLE.md) (see root AGENTS.md § "Code style") — do not restate the rules in this file.

- This source set runs tests against the REAL CLIPS engine (CLIPSJNI, 32-bit native library). Run ONLY via `./gradlew testClips` on the portable 32-bit JRE — it is NOT part of `./gradlew test` / `check` / `build`.
- The "Shared fixtures" section of the base AGENTS.md (fixtures.TestLocations / fixtures.TopologyConfigBuilder) does NOT apply here: tests in this module deliberately use the real shipped configuration (`DeckMapTopologyConfig.createDefault()`), not synthetic minimal topologies — the goal is to exercise the real `feis.clp` against real data.
- Each scenario needs independent engine state (`reportFireIncident` mutates evacuation/sealing/ACTION facts), but that no longer means constructing a fresh `ExpertSystemService` per scenario: `CLIPSJNI.Environment` has no public dispose API (only a private native `destroyEnvironment`, called from its own `finalize()`), so constructing/destroying many environments in one JVM process was found to reliably crash it (native `EXCEPTION_ACCESS_VIOLATION`, a GC-finalizer race). Instead, construct ONE `ExpertSystemService` per test class (`@TestInstance(Lifecycle.PER_CLASS)`, built in `@BeforeAll`) and call `resetForNewScenario()` in `@BeforeEach` — CLIPS's own `(reset)`, which clears facts/instances but keeps the loaded rule base intact (unlike `(clear)`, which wipes both — see `ClipsEnvironmentLifecycleTest`). Every class that touches the native engine must also carry `@Execution(ExecutionMode.SAME_THREAD)` and `@ResourceLock(FireScenarios.CLIPS_ENGINE_RESOURCE)` — the shared `Environment` is not thread-safe, and JUnit must never schedule two such classes concurrently even if parallel execution is ever enabled project-wide. `ScenarioGoldenMasterCheck` is a standalone `main()` diagnostic tool, not a JUnit test, so it isn't part of this constraint, but see its own in-code comment.
- This suite complements, does not replace, `clips.diagnostics.ScenarioGoldenMasterCheck` (broad net over 7 scenarios, full snapshot text diff against golden). Cross-check expected values in new tests against the recorded baselines in `src/testClips/resources/clips/diagnostics/golden/scenario-*.txt` — do not invent values independently, so the JUnit tests and golden-master cannot silently diverge on an unnoticed regression.
